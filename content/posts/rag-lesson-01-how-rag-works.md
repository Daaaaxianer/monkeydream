学习 RAG 之前，我最容易把它想成一个“接上知识库的聊天机器人”。这个说法听起来没错，却解释不了几个具体问题：资料到底放在哪里？模型每次都要读完整个知识库吗？回答错了，该检查模型还是检查检索？

“学习RAG基础知识”对话中的正式第一课，让我开始把这些问题连成一条清楚的流程。这篇文章是我的整理：先不急着记框架的调用方式，先弄清楚一次回答是怎样发生的。

> 本篇记录概念学习。文中的知识库规模、切块参数、检索分数和问答场景均为教学示意；实际的 Embedding 检索与 BioRAG 项目留到后续实践。

## 从一个我会真正关心的问题出发

假设我收集了 100 篇可变剪接相关论文，然后问模型：

> SUPPA2 在什么情况下无法计算 differential splicing 的 p-value？

模型可能了解 SUPPA2，也可能生成一段措辞专业的解释。但它未必读过我收集的这些论文，更不能仅凭回答流畅，就认定它找到了对应的方法依据。

换成我自己处理这个问题，通常会先查论文或软件文档，定位统计检验的相关段落，核对版本和适用条件，再组织回答。

**RAG 把类似的工作过程放进了 AI 系统。** 它的全称是 Retrieval-Augmented Generation，即检索增强生成：先找到相关资料，再把这些资料提供给大语言模型，让模型据此回答。

我现在会把三个词理解成三个动作：

| 环节 | 我对它的理解 |
| --- | --- |
| Retrieval，检索 | 从资料库中找到可能回答问题的内容 |
| Augmentation，增强 | 把资料与问题一起放入模型本次可见的上下文 |
| Generation，生成 | 由模型阅读这些内容，组织答案 |

“开卷考试”是个好记的比喻：检索器负责找书页，模型负责阅读和表达。不过，允许翻书也可能翻错页，拿到正确书页也可能理解错。这一点决定了 RAG 后面该怎么评价。

## 一张图，把建库和问答分开

我之前只看到“问题 → RAG → 答案”，现在会先把系统拆成两个阶段。

[![RAG 分为建库与问答两个阶段；问题既用于检索，也进入最终提示，知识库返回原文和来源](../../../assets/uploads/rag-lesson-01/pipeline.svg)](../../../assets/uploads/rag-lesson-01/pipeline.svg)

*图 1｜以向量检索为例的基础 RAG。建库在资料接入或更新时进行；问答时读取已有索引。点击图片可查看大图。*

**建库阶段（Indexing）**：把 PDF、网页、Word 等资料解析成文本，切成片段，生成向量，再保存文本、向量和来源信息。它通常不需要在每次提问时完整重做。

**问答阶段**：把问题编码成可检索的表示，找到相关片段，将问题、片段和回答要求组成提示，再交给模型。

图里有一条容易漏看的路径：**原始问题也要进入最终提示**。问题向量用于找资料，原始问题则告诉模型究竟要回答什么。检索器返回的也不能只有向量，模型需要读的是片段原文。

这张图展示的是常见的向量检索路线。RAG 也可以使用关键词检索或混合检索，并不限定必须有向量数据库。

### 为什么不把所有论文一次塞进去？

第一课用了一个直观的估算：假设每篇论文 8,000 tokens，100 篇约有 800,000 tokens；眼前的问题可能只需要其中几篇的几个段落。这些数字只是示意，也不代表所有模型的上下文限制。

我理解的关键是：**能放入很多内容，与值得为每个问题放入所有内容，是两回事。** 全量输入可能增加费用和等待时间，还会混入大量无关信息。RAG 尝试为当前问题挑选一份更集中的阅读材料。当然，挑选过程本身也会漏掉证据。

## Chunk：先把资料切成能读懂的片段

Document 是整份知识来源，Chunk 是切分后的文本块。在这条基础流程中，实际被检索的通常是 Chunk。

一篇 SUPPA2 论文可能同时包含背景、方法、统计分析和性能比较。查询某个检验步骤时，我需要的往往是方法中的一段，而不是全文主题的概括。将长文拆开，可以让检索更容易定位局部内容。

但切块也不能只顾长度。把一句话、一个限定条件或表格注释切断，检索到的片段可能就不完整了。

[![文本切块重叠示意：每块100个token，相邻块重叠20个token；跨越边界的句子在第二块中得以完整保留](../../../assets/uploads/rag-lesson-01/chunking.svg)](../../../assets/uploads/rag-lesson-01/chunking.svg)

*图 2｜Overlap 为边界处的语义留出缓冲。100/20 仅用于画图说明，并非通用参数建议。*

我会把切块的权衡记成三点：块太大，容易夹带无关内容；块太小，容易失去上下文；适当重叠能减少边界信息丢失，但会增加重复内容和存储开销。

第一课举过 `500 tokens / 100 tokens overlap` 的例子。真正实践时，我还需要明确单位是 token、字符还是词，并结合标题、段落和表格结构调整，而不是照抄一个数字。

## Embedding：让问题和资料能够比较

问题和答案所在的段落，未必使用同样的措辞。例如，“RNA-seq differential expression”和“Differential gene expression from RNA sequencing”在字面上不同，却在讨论相近的内容。

Embedding 模型会把文本映射成一串数字，也就是向量。合适的模型希望让语义相关的文本在同一个向量空间中更接近。问题也要编码到兼容的空间，才能与资料比较。[Sentence Transformers 的语义检索文档](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)给出了这一过程的解释，也提醒要区分问题与文档的编码方式。

[![语义空间的概念示意：RNA-seq差异表达问题靠近相关片段，远离烹饪片段；右侧展示Top-3按示意分数选取候选](../../../assets/uploads/rag-lesson-01/semantic-search.svg)](../../../assets/uploads/rag-lesson-01/semantic-search.svg)

*图 3｜左侧是为了理解而绘制的二维示意，不是真实向量降维结果；右侧分数也为人为设定，不是模型实测值。*

这里的“接近”需要由相似度或距离度量来定义。余弦相似度就是常见方式之一，它比较两个非零向量的方向是否接近。第一课我先记住直觉，具体计算留到下一课动手完成。

同时我得提醒自己：**语义相似不等于已经回答了问题。** 一段介绍 SUPPA2 的背景文字，可能与问题很相近，却没有说明 p-value 无法计算的具体条件。Embedding 提供的是检索信号，仍需要查看原文。

## Retriever 与 Top-K：找到候选，还要判断是否够用

Retriever 是执行检索的组件。采用向量检索时，它根据问题向量从索引中寻找相近的文档块，再把对应的文本和来源取回来。

`top_k = 3` 表示取排名靠前的三个候选。图 3 中的三个高分片段只是演示这个动作，分数既不是答案正确率，也不存在一个适用于所有模型的“超过 0.8 就相关”的门槛。

K 的选择也有取舍：太小可能漏掉关键证据，太大可能把重复或无关的片段带进模型上下文。更容易忽略的是，即使资料库里没有答案，Top-K 仍然可能返回若干结果。所以“检索有返回”并不意味着“证据已充分”。

资料很少时，可以逐个比较向量；规模增大后，向量索引或数据库能帮助加速搜索。第一课提到了 FAISS、Milvus、Qdrant 等工具，我先记住它们在系统中的位置。其中 [FAISS 是向量相似度搜索与聚类库](https://github.com/facebookresearch/faiss)，应与提供更完整数据管理能力的向量数据库区分开。

对我想做的论文知识库而言，每个片段还应该带着标题、作者、年份、DOI、章节或页码等元数据。**找到一句话，和知道这句话来自哪里，同样重要。**

## Augmentation：增强的是本次上下文

这是第一课帮我厘清的一个关键点：基础 RAG 在回答时，把外部资料放入模型的上下文，通常不修改模型参数。

我把 Context 理解为模型本次可见的内容，其中包括检索片段；Prompt 则把问题、资料和回答要求组织起来。一个最小提示可以写成：

```text
请依据下列资料回答问题。

资料：
[1] 片段原文（文档标题、章节或页码、版本）
[2] 片段原文（文档标题、章节或页码、版本）

问题：SUPPA2 在什么情况下无法计算 differential splicing 的 p-value？

请在相应论断旁标注资料编号。
如果资料不足，请说明还缺少什么依据。
```

这段提示没有填入真实的 SUPPA2 结论，因为这里要解释的是资料如何进入模型。真正回答那个问题，还需要检索并核对相应文档。

随后才轮到 Generation：模型根据问题与上下文组织回答。提示中要求引用，有助于核验，但引用编号本身并不能证明答案正确；我仍然需要检查对应段落是否支持具体说法。

## RAG、微调和后面的优化，各自改变什么？

我现在用“改变了什么”来区分 RAG 与 Fine-tuning（微调）。

| 比较点 | 基础 RAG | 微调 |
| --- | --- | --- |
| 主要改变 | 本次输入的资料与上下文 | 模型参数 |
| 更新资料的常见做法 | 更新文档及索引 | 准备训练数据并训练 |
| 常见目标 | 让回答使用指定或新近资料 | 调整任务表现、输出格式或行为 |
| 来源核验 | 可以保留片段与元数据，引用仍要检查 | 参数更新本身不提供逐条来源 |

如果目标是回答昨天更新的内部 SOP，我会先考虑如何检索到正确版本；如果主要问题是模型的任务行为或输出格式，再评估是否需要微调。这是起步判断，两种方法也可以结合。[RAG 的经典论文](https://arxiv.org/abs/2005.11401)本身就研究了检索与生成模型结合训练的方案，因此不能把所有 RAG 都理解成“永远不训练”。

后面会遇到的 BM25、Hybrid Search 和 Reranker，也可以放回同一条流程里：

| 组件或方法 | 在流程中帮什么忙 |
| --- | --- |
| BM25 等关键词检索 | 利用词项匹配；对基因名、软件版本、数据集编号等精确字符串值得保留这类信号 |
| Hybrid Search，混合检索 | 结合关键词与向量检索结果 |
| Reranker，重排序 | 对已经召回的候选做更细致的相关性排序 |
| LLM | 阅读最终提供的上下文并组织回答 |

例如“先召回 30 段，再重排选 6 段”，只是帮助理解的流程示例。我不需要第一课就把它们都装起来，先知道它们分别在哪里发挥作用即可。

## 回答错了，先看检索出了什么

第一课里，我最想留下的一句话是：**排查 RAG 时，先问 Retriever 到底找到了什么。**

[![RAG两类失败：正确证据未被召回是检索失败；已拿到充分且正确的证据仍然答错是生成失败，两者要分别评价](../../../assets/uploads/rag-lesson-01/failures.svg)](../../../assets/uploads/rag-lesson-01/failures.svg)

*图 4｜用两个简化案例区分检索失败与生成失败。实际系统也可能两者同时存在，或知识库本身缺少正确资料。*

如果知识库里有答案，却没有把正确片段送到模型面前，我应该检查解析、切块、过滤和召回过程。如果上下文已经包含充分且正确的证据，回答仍然误读条件或补造内容，就需要进一步检查提示和生成过程。

这也解释了为什么评价要拆开。检索端问“找对了吗、漏掉了吗”，后续会学习 Recall@K、MRR、NDCG 等指标；生成端问“是否忠实于资料、是否回答了问题、引用是否支持论断”。只展示一条漂亮回答，无法说明整个系统可靠。

RAG 为回答增加了可核验的资料入口，但资料质量、检索过程和模型理解都可能出错。我希望以后做出的系统，既能展示依据，也能在资料不足时说明边界。

## 用自己的话，重新解释一遍

现在让我向一个不了解 AI 的人解释，我会说：

> RAG 就是让 AI 回答前，先从指定资料里找出相关片段，再带着这些资料回答，并留下可以回头核对的出处。

如果把第一课的术语压缩成一张随手查的表，我会这样记：

| 术语 | 一句话理解 |
| --- | --- |
| RAG | 检索资料、增强上下文、再生成答案的组合流程 |
| Document | 原始知识来源，如一篇论文 |
| Chunk | 从资料中切出的文本单元 |
| Embedding | 把文本映射成向量的过程或表示 |
| Vector | 用于比较的数值表示 |
| Semantic Search | 利用语义表示检索相关内容 |
| Retriever | 找出并返回相关资料的组件 |
| Top-K | 取排序靠前的 K 个候选 |
| Context | 模型本次可见的上下文，包括提供的检索资料 |
| Generation | 模型根据输入组织答案 |

第一课还留下了几道很适合复习的自测题：

1. Embedding 模型和 LLM 分别负责什么？
2. 为什么长论文通常需要切块？重叠解决了什么问题？
3. `top_k = 5` 能否保证找到五条有用证据？
4. 证据已充分且正确，模型仍然答错，该优先检查哪一端？
5. 要回答昨天新发布的 SOP，为什么通常先考虑检索这份资料？

<details>
<summary>展开我的参考答案</summary>

<p>① Embedding 为检索提供可比较的数值表示，LLM 阅读上下文并组织回答。② 切块帮助定位局部内容，重叠减少边界信息丢失。③ 不能，Top-K 只表示排名与数量。④ 优先检查生成端，同时核对证据是否确实足够。⑤ 首先需要取得最新、正确版本的资料，而基础 RAG 能在回答时将它提供给模型。</p>
</details>

下一课，我准备先用少量生物信息学短文本，完成真实的 Embedding、相似度计算和 Top-K 检索，直接观察系统找到了什么。之后再逐步接入 PDF、切块、向量索引和 LLM，向 Biomedical Paper RAG 推进。

对我来说，第一课的收获是终于能把“知识库问答”拆开理解。以后遇到 loader、splitter、embedding、vectorstore、retriever 或 prompt，我可以先把它们放回图 1，再去看各自的实现。
